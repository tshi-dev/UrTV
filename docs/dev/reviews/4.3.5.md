## Findings

### F1 [high] [fixed] The safe page dropped our default-home claim, and «حاول مرة ثانية» never put it back (Android 9)

- Where: `android/launcher/src/main/java/sa/urtv/home/SafeActivity.java` (onCreate)
- What a person sees: an Android 9 TV set up with the wizard kept: after the safe page and «حاول مرة ثانية», every Home press opened the setup wizard or a chooser instead of UrTV.
- Why: `clearPackagePreferredActivities` in onCreate; on Android 9 the preferred activity from `set-home-activity` is the only claim, and the app cannot write it back.
- Fix: removed (e4394e9a); crash_loop_test pins its absence.

### F2 [medium] [fixed] «افتح الشاشة الأصلية» could open the setup wizard or a Settings stand-in

- Where: `SafeActivity.stockHome`
- What a person sees: the focused button opened the TV's setup wizard on a set-up TV, or a dead toast on TVs whose stock home our setup turned off.
- Why: the first non-UrTV HOME was taken, only com.android.settings skipped.
- Fix: StockHome.real with SetupEngine.otherHome's exclusions; no stock home: no button, the retry has the focus (e4394e9a).

### F3 [medium] [fixed] Any crash of the home's process counted toward safe mode, a background service or receiver too

- Where: `CrashLoop.crashed`
- What a person sees: a crash-looping service (TypeService, MusicService, a boot receiver) took the working home screen away.
- Why: crashed() did not ask whether the home screen was opened in that process.
- Fix: a crash counts only with `openedAt > 0` (e4394e9a).

### F4 [medium] [fixed] Disk and fsync on the UI thread at every cold start (R1)

- Where: `CrashLoopStore.hook`, `MainActivity.onCreate` (safe), `SafeActivity` (clear)
- What a person sees: the first frame and the remote held on a slow TCL while the crash file was synced.
- Why: started() was written synchronously so the handler could read it.
- Fix: the state lives in memory; the file is written on the store's thread; safe() reads the memory copy (e4394e9a), completed by F7 (bc7754bc).

### F5 [low] [fixed] Safe mode outlived an update that fixes the crash

- Where: `CrashLoop` (no version in the file)
- Fix: the file keeps the versionCode; a new version starts with nothing counted (e4394e9a).

### F6 [low] [open] No WebView: the card disappears without a word, and one failure turns it off for the process (R2)

- Where: `WebViews.java`, `HomeCard.java`
- What a person sees: on a TV without a WebView the home shows no card and no line why (the report says «WebView: none»); a one-off failure (WebView being updated) keeps the card off until the process ends.
- Smallest fix: retry after a while (the next onResume after 60 s); one quiet line where the card would be. Proposed for 4.4; the home itself works.

### F7 [medium] [fixed] The UI thread could still wait on the background fsync through the shared lock

- Where: `CrashLoopStore` (LOCK held across write by the background writer)
- Fix: LOCK guards the state only; FILE_LOCK guards the disk; the writer re-checks the state with the file held, so a crash write is never overwritten (bc7754bc).

### F8 [low] [fixed] The safe page's text told the person to open a stock home that was not there

- Fix: without a stock home the body is the retry line only (bc7754bc).

### F9 [medium] [open] The built pages still fail the ES2017 parse rule (#19, WebView 66)

- Where: `src/template.html` (a regex lookbehind and object spreads), dist/tv.html and tv-en.html
- What a person sees: on an Android 9 TV stuck on WebView 66 the page's script never starts (a blank layout). Shipped the same in 4.3.4: 4.3.5 does not make it worse.
- Why: next's 9a8b4953 («#19: the page parses as ES2017») is not on the 4.3.x line.
- Smallest fix: cherry-pick 9a8b4953 (template, dist, tests/es2017_parse.test.mjs, acorn in CI). Left to the owner: it changes CI on a hotfix line.
