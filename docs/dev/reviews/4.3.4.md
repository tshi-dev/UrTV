## Findings

### F1 [medium] [open] «التطبيقات المخفية» stays asked after a cancelled PIN: the next «انقل» opens on «المخفية» or does nothing

- Where: `android/launcher/src/main/java/sa/urtv/home/MainActivity.java:2395` (set), `:2405` (kidsNoEdit returns), `:3869` (a cancelled PIN
  runs `() -> { }`), `:2429-2433` (the only place that clears it)
- What a person sees: on a TV with «قفل الإعدادات» on, the person picks Settings ← «ترتيب كل التطبيقات» ← «التطبيقات المخفية». The home asks
  for the PIN (onNewIntent clears Parental.SESSION) and the person presses Back. Later, in the same home process, they long-press an app in
  the grid and choose «انقل». If nothing is hidden, the toast says «ما فيه تطبيقات مخفية» and the move mode does not open. If something is
  hidden, the mode opens on «المخفية» with its list instead of on the app they pressed. It happens once, then the flag is cleared. The same
  happens after the request was refused in kids mode and kids mode was then turned off.
- Why: `appsRequested` sets `wantHiddenList = true`. Only `startAppsEdit` reads and clears it, and that runs only after `guarded(...)`
  succeeds. `kidsNoEdit()` returning early, a cancelled PIN, or `startAppsEdit` returning early (`appsEdit != null || edit != null`) all
  leave it set. `beginAppsEdit(pkg)` from the app's «انقل» (`:2756`) then reaches `startAppsEdit`, which takes `toHidden = true`.
  Confirmed by reading every assignment of `wantHiddenList` (3 lines in the file) and the cancel path of `guarded`.
- Smallest fix: in `beginAppsEdit(String pkg)`, add `if (pkg != null) wantHiddenList = false;` as its first line, because only the
  settings' request has `pkg == null`. Another way: pass `toHidden` through `beginAppsEdit`/`startAppsEdit` instead of a field.

### F2 [low] [open] Menu in «تعديل المفضلة» or «تعديل التطبيقات» now opens «المصادر» over the mode

- Where: `android/launcher/src/main/java/sa/urtv/home/MainActivity.java:4072` together with `FavEdit.owns` (`FavEdit.java`, 82 not owned;
  `tests/edit_keys_test.py` lists MENU among the keys that pass)
- What a person sees: on any TV, while an edit mode is on, a press of the remote's Menu key (perhaps looking for the app's options) opens
  the Inputs dropdown «المصادر» on top of the mode. This happens behind the «المصادر» lock when that lock is on. Before 4.3.4 the mode
  swallowed Menu. Picking an input leaves the home, and onPause saves the arrangement.
- Why: `editKey`/`appsEditKey` now return false for MENU. The first Menu branch (the app's options) checks `edit == null && appsEdit == null`,
  but the second one (`KEYCODE_MENU && ACTION_UP && !pills.isEmpty()` → `showInputs`) does not, so the key falls through to it. RemoteKeys
  does not handle MENU (checked).
- Smallest fix: add `&& edit == null && appsEdit == null` to the Inputs branch at `:4072`. Every other key still goes on as R-010 wants.
