## Findings

### F1 [high] [fixed] Host setup stops for good at «safe» (and «mine», «community») on every TV without `cmd`: Android 6 and older

- Where: `optimize/disable.sh:76-83` (HANDLERS and its fail-closed check), reached from `optimize/run.sh:205` (step safe), 209 (mine) and `optimize/community.sh:77`
- What a person sees: an Android 5.x or 6.0 Android TV (a 2015/2016 Sony Bravia, Philips or Sharp that never got Android 7; Fire OS 5 sticks) set up from a computer: run.sh prints «!! disable.sh: the TV did not say which apps open its Settings and its channels, so NOTHING was turned off» at the safe list, every time, and the setup cannot go past that step. In 4.3.5 the same TV went through: Android 6 had its safe list applied (the input guard reads the 6.0 dump), Android 5 had everything left on by the guard's NOCHK and the step passed. tcl-safe.txt names Google packages that every Android TV of that age has (tvrecommendations, backdrop, feedback, partnersetup), so `intended` is never empty there.
- Why: `cmd` came with Android 7 (tweaks.sh already skips `cmd package compile` below SDK 24); on 5/6 every `cmd …` line prints only to stderr, which HANDLERS drops, so the answer is the two markers and END_OF_LIST: no Settings line, the fail-closed branch. The `!!` row in SETUP-PROMPT then says to report, so the agent stops. The on-TV setup is not affected (the launcher is minSdk 26). Related, smaller: on Android 7 the guard relies on `--brief` printing the bare `pkg/class` line; selftest.sh already falls back to a query without `--brief` «where the TV knows it», disable.sh has no such fallback, so a TV whose `--brief` is unknown or prints otherwise would also fail closed here (the home query of community.sh has the same dependency, so this part is not new for community lists, but it is new for the safe list).
- Smallest fix: put the SDK in the answer (`s=$(getprop ro.build.version.sdk); echo "== sdk $s"; …`) and below SDK 24 read the handlers from `dumpsys package r` instead (its «Activity Resolver Table» names the components under `android.settings.SETTINGS:` and the other actions), or at least do not fail closed there: say «Left on by name only: this TV (Android 6 or older) cannot be asked which apps open its Settings» and go on with keep.txt's names. Add a fake-TV case with no `cmd` (SDK 23) to input_guard_test. Optionally retry a `--brief` query that named no Settings app once without `--brief` and take `packageName=`.
- Fix: 4c933351 (and b4f01e84 for the note). HANDLERS now starts with `== sdk $(getprop ro.build.version.sdk)`. Below SDK 24, disable.sh turns nothing off, prints an English and Arabic note on stderr and exits 0, so run.sh goes on. It writes the intended packages to inputs-left.txt, so community.sh counts none of them as applied. Checked: input_guard_test runs a fake SDK 23 TV (exit 0, no disable command, the note, the packages in inputs-left.txt). The `--brief` part is covered by F4's fix: a TV that answers neither Settings nor Home still fails closed, which is right for «no answer». The on-TV side needs no sdk branch (minSdk 26).

### F2 [medium] [fixed] The factory-interface step fails after it already switched the home and turned the stock home off, says «we turned off nothing», and offers no undo

- Where: `android/launcher/src/main/java/sa/urtv/home/setup/SetupEngine.java:850-866` (factoryOff: home(), the stock home off, then debloat()), with the new `return failed(InputGuard.HANDLERS_SAID)` at 235; `FactoryActivity.java:65` shows «رجّع واجهة المصنع» only when the FACTORY mark starts with «on»
- What a person sees: on a TV where the handler question fails (cut, or the TV names no Settings app: F4), «تعطيل واجهة المصنع» ends with «ما اكتمل» and HANDLERS_SAID («…فما أوقفنا شيئاً»), but the home is already UrTV's and the stock home is already disabled; opening the screen again shows the offer, not «رجّع واجهة المصنع». Before 4.3.6 the same order existed for the input guard, but that failure is transient; this one can be permanent on such a TV.
- Why: debloat()'s guards run after the two changes; the mark is written only when debloat() is DONE. The stock home itself is also never put to the handler question.
- Smallest fix: in factoryOff() (or factoryOffer()) ask `InputGuard.handlers(text(InputGuard.HANDLERS))` before home(): null is a refusal with nothing changed, and a stock home package that is in the set is not turned off (the step goes on with the safe list only, with a line).
- Fix: 4c933351. factoryOff asks `InputGuard.handlers(text(InputGuard.HANDLERS))` right after the offer, before the ledger, `home()` or any command. Null is HANDLERS_SAID with nothing changed. A stock home that is in the set is refused with «… فما عطّلناها. ما تغيّر شيء.». The FACTORY mark is written once the stock home is off, before debloat()'s result is looked at, so «رجّع واجهة المصنع» is offered and the boot guard is armed even when the list step fails (a missing boot-guard.txt is a clean state, BootGuard.State.parse). input_guard_test pins the order. Still possible: an IOException between the stock home going off and the mark leaves no mark. That path was there before, is not new, and FactoryActivity's message names the restore.

### F4 [medium] [fixed] «No Settings app named» is treated as «the TV did not answer»: a TV whose Settings app does not declare android.settings.SETTINGS loses every list, on both sides, for good

### F7 [medium] [fixed] On Android 9 and 10 TVs homeKeyLost is still always «lost»: the in-home key filter that froze the Percee stays on there

- Where: `SettingsKey.java:127-129` (`homeKeyLostApplies`: leanback and SDK ≥ 28), `TypeService.java:135-136`, `SettingsKey.java:107` (`if (homeFront && homeKeyLost) return true;`, before the weak-TV rule)
- What a person sees: an Android 9 or 10 Android TV (most TCLs of 2019–2020) with the phone-typing service on: while our home is in front, every remote key goes through TypeService and waits on the home's main thread. This is the mechanism the commit names for the Percee freeze, and it applies on a 2 GB TV too, because the in-home rule comes before Ram.low. It was the same in 4.3.5 (not made worse). But the fix says it is limited to «a TV whose system takes the key», and on 9/10 it is not.
- Why: `android.app.action.TOGGLE_NOTIFICATION_HANDLER_PANEL` is an Android 11 action. It is in NotificationManager of android-all 14, but not in the 8.0 or 9 jars this repo's tests cache. Android TV's SystemUI of 9/10 never declares it, so `queryIntentActivities(...).isEmpty()` is true there, just as the test's own lostask comment says for Android 8 («it was always «lost» there»).
- Smallest fix: ask homeKeyLost only from SDK 30 (`leanback && sdk >= 30`; the Haier on 14 is unchanged), plus settings_key cases `lostask 28 tv → no`, `lostask 29 tv → no`, `lostask 30 tv → yes`. To check on a 9/10 TV: the UrTVType log shows `settings key=homelost` once per service start.
- Fix: e9ae6e2e. `homeKeyLostApplies` is now `leanback && sdk >= PANEL_ACTION_SDK` (30), so on Android 8, 9 and 10 homeKeyLost is false and the filter is off while our home is in front, as before the Haier change. The Haier on 14 is unchanged (lostask 30 tv → yes, filter5 home off low lost 34 → on). The settings_key cases for 28/29 tv → no and 30 tv → yes are right. They run and pass at 74a3fe08 (F10).

### F8 [low] [fixed] The catch-all in onKeyEvent gives the key back without a word

- Where: `TypeService.java:84-90`
- What a person sees: nobody, unless it fires. Then on the Haier path (TO_HOME) or outside the home (OPEN_TV_SETTINGS), the Settings key silently does nothing, and the tester's UrTVType log has no line for it.
- Why: `catch (Throwable t) { return false; }`. It cannot change a decision other than the one that failed: the only work after `decide()` is `new KeyEvent(e)` and `main.post`. Returning false is the right fallback, but `holding` may stay set until the next press, which resets it. It also swallows Errors (OutOfMemoryError) with no trace.
- Smallest fix: log one fixed word in the catch (`log("settings key=error")`, never the key or the exception text), at most once per service.
- Fix: e9ae6e2e: `log("settings key=error")` in the catch (Log.i with a fixed word; no key, no exception text). It logs on each failing key, not once per service. That is acceptable: the path is exceptional and the line is short. The test pin for it is the line that breaks settings_key_test (F10).
